# 其他设备接入轮换后的同步密钥

更新：2026-10-08，0.1.38 (39)。本页描述已绑定设备的换钥接入；0.1.39 已接入[本机发起轮换界面](SYNC_ROTATION.md)。

## 操作步骤

1. 另一台设备完成密钥轮换并发布后，本机普通同步会停止并提示密钥变化。
2. 打开 **GitHub 同步 → 接入新同步密钥**，选择新同步口令或新恢复码。
3. 输入从轮换设备保存的新凭证，勾选确认，点击“验证并接入新密钥”。这是独立同步口令，不是本机保险库主密码。
4. 成功后点击“立即同步”，再合并主机、身份、文件夹和片段；有冲突时继续由用户选择保留版本。

接入操作只读取远端并更新本机密钥，不提交 GitHub、不自动应用远端业务数据。凭证输入在请求开始时清空，失败后需重新输入；切换验证方式和关闭窗口也会清空。操作进行中可取消，界面等待核心返回后解除忙碌状态。

## 校验与原子切换

- 使用已保存的仓库/分支和数字仓库 ID，不接受换仓库或另一同步空间的密钥。
- 验证远端提交为本机已知历史的后续提交，从同一提交读取信封和密文。
- 用用户输入的新口令或恢复码解开信封，校验空间、信封认证以及快照完整性。
- 完成解密后再次读取远端，确认提交和两份文件均未变化，再次核对仓库身份。
- SQLCipher 事务内同时保存旧密钥到历史、安装新密钥、保存新读取下限并使旧冲突审阅失效。任一步失败全体回滚。
- 沿用最多 16 把历史密钥的上限，不自动淘汰；已保留的历史密钥禁止被重新设为活动密钥。
- 重试已经成功接入的同一密钥时，会验证凭证后提示本机已经使用当前密钥，不重复归档。

## 保留合并基线与防回退

切换密钥不等于已经合并远端数据。因此保留 `base`、`local` 和已确认的 `remote_revision`，避免跳过用户尚未处理的远端修改或本机编辑。

同步状态增加可选 `key_revision`，记录已验证的新密钥提交。接入后普通同步至少从该提交或其后代读取，即使退出重开也不会退回接入前的历史。普通同步确认完成后，新的 `remote_revision` 接替此下限，清除 `key_revision`。未完成这次普通同步前，核心拒绝再次发起本机轮换。

旧状态没有该字段时按无下限处理，兼容已有数据库。尚有此字段的状态不适合交给旧版本处理。保险库 schema 和远端密文协议不变。

## 当前边界

- 有待处理批次、发件箱、发布记录或本机轮换候选时禁止接入；不会用新密钥覆盖待核对的旧发布状态。界面提示先恢复原批次。如果旧发布结果未知且远端已经换钥，本轮仍保留并阻止操作，尚无强制解除流程。
- 口令/恢复码错误、远端损坏、验证中再次变化、仓库身份变化或写入失败都不改变现有密钥和业务数据。
- 旧密钥只可读取本机已留存的历史；新恢复码不能找回本机从未拥有过的历史密钥。
- 旧冲突列表的密钥/远端版本可能已过时，接入成功后需重新同步生成审阅；不会自动采用之前未确认的选择。
- 两次读取之间可检测远端变更，但无法锁住 GitHub 分支。最终复核后若远端再次轮换，下次同步仍会停止并要求接入最新密钥。
- 0.1.38 本轮未增加本机发起轮换 UI，后续 0.1.39 已补齐；自动后台同步、真实账户操作或 SFTP 新功能均不在本轮范围。
