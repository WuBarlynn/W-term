# 同步密文发件箱

更新：2026-10-05，0.1.29 (30)。这是 Rust 内部同步编排；0.1.31 已接入 [GitHub HTTPS 传输](SYNC_GITHUB.md) 的本地测试，仍无应用界面、后台任务或真实仓库验收。

## 流程

1. `state::prepare` 完成合并，保存不可变候选及待上传批次。
2. `outbox::stage` 使用 IMMEDIATE 事务复核同步操作版本、当前仅本机依赖和待上传候选。首次生成密文包及密钥信封，保存后才返回可发送内容。
3. 同一批次重试、锁定后重开或关闭数据库后恢复，都返回原来的密文和信封字节。发送失败或结果未知时保留发件箱，不重新加密，不确认检查点。
4. 后续传输适配器从同一已验证的远端提交读回两份文件，核实仓库、分支、提交父版本，然后调用 `outbox::acknowledge_published`。
5. 核心核对操作版本、批次、父提交、密文及信封逐字节一致，并认证解密本机保存包、与不可变候选比较；随后在同一事务推进检查点、清除发件箱、保存小型确认回执。

普通状态确认接口在存在发件箱时拒绝操作，防止跳过密文核对。只需拉取的批次不创建发件箱，沿用拉取确认流程。

## 中断与重复请求

- 首次持久化失败：不返回待发送字节，原待处理批次保留。重试可以重新生成，因为尚未允许发送。
- 已持久化但未发送或响应丢失：重试返回原字节。只凭网络超时不能取消批次。
- 远端内容不符、父版本错误、操作已过期、发件箱损坏：拒绝确认，保持原记录；即使新密文解出相同明文，也不能代替已保存的密文字节。
- 写确认回执失败或删除发件箱失败：整个事务回滚，检查点和密文都保留。
- 已确认成功但调用方没有收到结果：同一批次、操作版本、父提交、远端版本及两份内容摘要可重复确认。回执在 SQLCipher 内保存 SHA-256 摘要，不长期保留上一批完整密文。
- 旧确认在下一批准备后重到：不会确认或清除下一批。若另一批已经确认成功，过旧回执拒绝。
- 只有传输确认远端未接受批次后，才能调用取消。取消与清理发件箱同事务，不回滚用户数据；之后重新合并会得到新批次与新密文。没有提供“忽略未知远端结果”的自动取消。

`stage` 每次重新检查仅本机依赖；如果本机专用主机在等待期间关联了待上传身份，阻止继续发送已保存密文。但若原请求在途并且远端确已接受，确认必须记录真实发布，不能因本机后续修改而假装没有发布。确认只更新同步检查点，不覆盖之后的业务编辑。后续撤回仍需专门流程，不能承诺清除仓库历史。

## 存储与边界

- 沿用 SQLCipher schema 3。`metadata.sync_outbox_v1` 保存版本、操作版本、批次、密文及密钥信封，外层 JSON 上限 32 MiB；内部快照包仍遵守加密模块 24 MiB 上限。
- `metadata.sync_delivery_receipt_v1` 保存最近一次内容核对回执，上限 4 KiB。缺字段、未知字段或容量超限拒绝，不静默当作空状态。
- 每次恢复会核对密钥信封与本机密钥、认证包并比较待上传候选。损坏条目不会被新密文覆盖。
- `crypto::encrypt_pending` 仍是一次性内存加密辅助函数；网络发送必须走 `outbox::stage`，不能使用这个辅助函数重试上传。
- 本层没有网络，也不验证某个提交真实存在、属于指定分支或仍为远端最新提交。传入本机原字节并虚构提交号不能算真实发布证明。传输必须提供经验证的提交来源及祖先关系；两个文件必须在同一提交中原子发布，不能分别写入。
- 0.1.30 增加 [本机分阶段密钥轮换](SYNC_ROTATION.md)。仍没有远端并发写入、回滚保护、同步 UI 或真实进程终止/断电验收。保险库的现有“恢复为新记录”不复制发件箱和同步检查点。

## 自动化

新增 8 项测试，覆盖关闭/重开后稳定字节、持久回执重复确认、保留后续编辑、远端内容及父版本不符、有效但不同快照替换、损坏和过期记录、容量限制、首次保存/确认/取消失败回滚、取消后新批次、隐私依赖变更、仅拉取及旧回执不影响下一批。

测试使用临时 SQLCipher 库、生成密钥、合成凭证及模拟提交号。运行 `cargo test --manifest-path rust/Cargo.toml --locked sync::outbox`。这些测试不代表真实 GitHub 发布或 Apple 真机验收完成。

## 轮换整合（0.1.30）

轮换批次暂存使用已核验恢复码的候选密钥；普通批次使用活动密钥。内容确认事务还负责历史密钥保存和候选激活；普通取消同时清除候选。具体错误保护及其他设备接入边界见 [SYNC_ROTATION.md](SYNC_ROTATION.md)。

0.1.31 起存在 GitHub 发布记录时，直接确认及取消会被阻止；确认必须通过远端提交核对，并与发布记录删除共用事务。


0.1.37 起，GitHub 传输可对“分支更新从未发出，或首次明确被拒绝”的普通批次，在核对远端后原子取消旧发布记录/发件箱并重新合并。未知结果与旧版日志继续保留；见 [竞争恢复](SYNC_RECOVERY.md)。
