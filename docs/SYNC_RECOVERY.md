# 同步竞争后的恢复

更新：2026-10-08，0.1.37 (38)。入口仍是 **GitHub 同步 → 恢复待处理同步**。

## 用户流程

当本机已经准备好同步内容，而另一台设备抢先更新了远端分支时，本次发布会停止。再次点击“恢复待处理同步”：

1. 核对旧批次是否已发布。已发布的仍按原提交、父版本和密文字节完成确认。
2. 能证明旧批次未发布时，核对仓库身份、远端历史、密钥与加密内容，再取消旧批次的发布记录。
3. 保留本机全部当前业务数据，包括失败之后的编辑，重新读取远端并执行三方合并。
4. 无冲突则发布新批次；有冲突则保留双方，进入既有“处理同步冲突”流程，由用户选择。

不需要删除本机主机或重建同步空间。每次点击最多进行一轮重新合并；若另一台设备再次抢先发布，仍保留新的待处理批次，不无限自动重试。

## 如何判断未发布

发布记录新增 `ref_update_started`：

- 创建 Git blob/tree/commit 期间为 false，这些步骤没有更新分支。
- 发出 PATCH 更新分支**之前**，先把 true 提交到 SQLCipher；写入失败则不发请求。
- 只有此前没有任何结果未知的 PATCH，且本次明确收到 HTTP 409/422 拒绝，才持久化恢复为 false。
- 网络失败、超时、5xx、响应丢失、成功后核对失败，都保持 true。之后一次拒绝不能证明更早的请求未被接受。
- 旧版记录没有这个字段，一律按 true 处理；不根据“目前远端看不到提交”推断未发布。

409/422 是 GitHub 更新引用接口的冲突/验证失败响应，参考 [GitHub REST references 文档](https://docs.github.com/en/rest/git/refs#update-a-reference)。本实现不解析或展示服务端正文，避免把令牌等内容带入错误消息。

即使记录为 false，也只有在远端确实变化时才重新合并。仅因分支保护、验证规则或限流导致拒绝，但分支没变化时，不会反复清空并新建批次。

## 数据保护与边界

- 发件箱、发布记录和待处理状态在同一个数据库事务中清理；任一步失败全部回滚。
- 不回滚业务记录，不覆盖后续编辑，不删除远端的已创建 Git 对象；所有分支更新保持 `force: false`。
- 远端仓库 ID 不符、历史回退/分叉、密钥变化、文件损坏、网络错误时，不取消旧批次。
- 未发布的普通批次可恢复；密钥轮换批次暂不自动取消，避免使已保存的新恢复码和候选密钥失效。
- 旧版本或结果未知的批次继续保留：远端后续能证明已接受时可确认；不能证明时不会提供“强制丢弃”按钮。
- 非快进保护不能解决外部管理员强推和在途请求的全部竞态，仍不宣称严格 CAS 或真实 GitHub 验收完成。
- 新版写入的额外日志字段可能使旧版因未知字段拒绝处理，避免降级版本操作正在恢复的同步记录。

## 验证

新增本地 HTTP / SQLCipher 测试覆盖：

- 首次非快进拒绝、数据库关闭重开、保留后续编辑后重新发布。
- 未发送 PATCH 时远端抢先提交，重新合并产生冲突并保留双方。
- 503 后再次 422 仍不能取消；旧版日志保守处理。
- PATCH 前状态落盘失败不发请求；清理发件箱失败时整个事务回滚。
- 没有发布日志的待处理批次恢复；仓库身份变化和远端密文损坏不清理状态。

既有响应丢失确认、内容核验、隐私边界和密钥轮换测试继续执行。使用临时保险库和本地模拟 GitHub 服务，没有访问用户真实仓库或同步真实凭证。真实双设备竞争、断网及进程终止仍需签名设备验收。
